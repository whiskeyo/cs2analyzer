# Internationalization (EN / PL)

Ship the web UI in **English by default**, with **Polish** as the second locale. Two catalogs, one typed message helper, locale stored on the user-settings document. No extra locales in v1. Parser, stats formulas, and CLI stay English.

This plan is **UI copy only**. It does not add a first-run tutorial (separate work) and does not reintroduce KaTeX or a client-side markdown pipeline.

## Problem today

Every user-facing string is a literal in TSX or compile-time FAQ markdown. There is no catalog, no `locale` field, and no switch.

| Surface | Where copy lives | Localized? |
|---|---|---|
| Site chrome (brand, nav, pre-release tip, credits) | `Header.tsx`, `SiteNav.tsx`, `Credits.tsx` | No — English literals |
| Home / Analyzer / FAQ / Playbook pages | `pages/*.tsx` | No |
| Settings gear menu | `SettingsMenu.tsx`, confirm/merge dialogs | No |
| HUD, playback, scoreboard, sidebar tabs | `components/radar/`, `playback/`, `sidebar/` | No |
| Drop zone / parse progress | `DemoDrop.tsx`, `ParseProgressPanel.tsx` | No |
| FAQ articles | `content/faq/*.md` → Vite plugin → HTML | English only |
| Dates on saved notes | `toLocaleString()` with no locale | Browser default |
| Money | `toLocaleString("en-US")` in `loadout.ts` | Hardcoded US |
| User settings store | `UserSettings` in `userSettings.ts` | No `locale` (USER-SETTINGS listed it as v2) |

Theme / locale / 12h clock were deferred until i18n exists. The settings store is already in IndexedDB (`schema` 1, store `settings`). Pull `locale` forward into that document instead of a second persistence path.

## Product

- **Default locale:** `en`. First paint and reset-to-defaults are English.
- **Second locale:** `pl`. Only these two codes in v1.
- **Override required.** Browser language may *seed* an unset document (open question), but the user must be able to pick EN or PL and have that stick. Auto-detect-only is a non-goal.
- **One catalog shape** for chrome, settings, and (when it lands) tutorial copy. FAQ markdown is a later content phase, not the first catalog.

### Entry points

- **Settings** (gear today; the USER-SETTINGS modal when that UI ships): Language — English / Polski. Applies immediately; no reload if catalogs are already bundled.
- **Tutorial** (separate PR / plan): first-run copy reads the same helper and the current `settings.locale`. Do not invent a second catalog or a tutorial-only locale flag.

Changes apply to chrome and settings labels first. Long-form FAQ can stay English until the content phase.

## Approach: typed catalogs, not a framework

Two locales and a Vite + React app do not need `i18next`, `react-intl`, or ICU plugins. Those pull formatters, plural pipelines, and a runtime we would barely use.

Recommended shape (names illustrative):

```
apps/web/src/lib/i18n/
  locales.ts          // Locale = "en" | "pl"; DEFAULT_LOCALE = "en"
  messages.ts         // Messages type + t(messages, key, vars?)
  en.ts               // satisfies Messages
  pl.ts               // satisfies Messages
  catalogs.ts         // Record<Locale, Messages>
```

- **`Messages`** is a TypeScript interface (nested by area: `nav`, `settings`, `home`, `hud`, …). Both dictionaries `satisfies Messages`, so a missing PL key is a type error.
- **`t()`** is a small helper: dotted key or a function that takes the catalog object. Interpolation is `{name}` replacement only. Plurals: explicit keys (`kills_one` / `kills_other`) or a two-branch helper — CS2 UI has few real plurals.
- **Hook:** `useMessages()` reads `settings.locale` from `useUserSettings()`, returns the catalog + `t`. Fallback: if locale is unknown or IDB is down, use `en`.
- **`document.documentElement.lang`** set to `en` / `pl` when locale changes (a11y, browser translate hints).
- Catalogs are **eager** and tiny. Do not code-split PL until a third locale exists; a dynamic import for one extra dictionary is extra moving parts for no bundle win.

Avoid: `react-i18next`, Lingui, FormatJS, JSON files without types, stringly keys that compile when PL is incomplete.

### What stays untranslated (on purpose)

| Kind | Why |
|---|---|
| Map names (`de_mirage`, `Mirage`) | Game identifiers; layouts / share URLs use them |
| Weapon names / def indices | Icons + CSV stay Valve English |
| Scoreboard acronyms (`ADR`, `KAST`, `KD`) | FACEIT-style HUD; same in PL as in EN |
| Round-win reason codes, tick/formula constants | Parser / stats contract, not UI chrome |
| User content | Notes, playbook titles, imported JSON — do not rewrite |
| DEV layouts editor | Internal; English is fine until someone asks |
| CLI / Rust / WASM errors | Not the web catalog. Optional later: map a few parse-worker error *codes* to chrome strings |

## Locale on user settings

Add to `UserSettings` (same IndexedDB row, same `parseUserSettings` merge rules):

```typescript
export type Locale = "en" | "pl";

// on UserSettings
locale: Locale; // default "en"
```

- Unknown / missing → `"en"`.
- Reset-to-defaults → `"en"` (shipped behavior, not “whatever the OS is”).
- Do **not** put locale in `localStorage` beside the settings document.
- `html lang` and `t()` both read this field.

**12h clock** can wait. If we format clocks at all, use `Intl` with the active locale; a separate `hourCycle` setting is still a USER-SETTINGS v2 candidate, not required for i18n v1.

Theme stays deferred (dark only).

## FAQ / long-form content

FAQ is **not** a message dictionary. Articles are GFM compiled at build time (`faq-markdown` Vite plugin → `{ question, html }`). Remark stays off the client; do not bring it back, and **do not add KaTeX** (FAQ tests already assert no math / `.katex`).

Two honest options — pick one in the content phase (open question):

| Option | How | When |
|---|---|---|
| **A. EN-only FAQ in v1** | Keep `content/faq/*.md`. Chrome around FAQ (title, lead, nav) is translated; article bodies stay English. | Default if PL FAQ is not ready |
| **B. Dual files** | e.g. `content/faq/en/*.md` and `content/faq/pl/*.md` (same slugs). Plugin emits both; `Faq.tsx` picks the list for `settings.locale`, falls back to EN if a slug is missing. | When whiskeyo wants PL articles |

Do not invent a third path (one `.md` with `<!-- pl -->` blocks, or runtime markdown). Dual files reuse the existing compile plugin.

Home / Analyzer marketing paragraphs are **chrome** (catalog keys), not FAQ files.

## Phased plan

One behavior per commit. No `.dem` files. Tests next to `lib/i18n/` and the settings field.

### Phase 1 — Skeleton + EN / PL catalogs

1. `Locale`, `DEFAULT_LOCALE`, `Messages`, `en.ts` (current English copy extracted for chrome you are about to wire — start with nav + settings + home kicker, not every HUD string).
2. `pl.ts` with the same keys. Incomplete PL is a type error; fill Polish before merging the catalog commit.
3. `t()` + unit tests (missing key in tests only, interpolation, fallback to EN).
4. No UI switch yet; default catalog is EN so existing RTL tests keep passing.

### Phase 2 — Locale on settings + chrome

5. Add `locale` to `UserSettings` / `defaultUserSettings` / `parseUserSettings`. Tests: default `en`, reject `"de"`, merge missing field.
6. Settings control: English / Polski on the gear menu **or** the USER-SETTINGS modal if that UI is already there. Immediate apply.
7. Set `<html lang>`.
8. Wire **chrome**: `SiteNav`, `Header` (brand aria, pre-release, Export CSV), `Credits`, Home intro, FAQ page chrome, Settings menu labels, drop-zone empty states, parse progress.
9. Dates on saved notes: `toLocaleString(localeTag(settings.locale))` (`en` → `en-US` or `en-GB` — open question; `pl` → `pl-PL`). Money can stay `$` + western digits unless we decide otherwise (open).

### Phase 3 — Remaining app chrome (same catalogs)

10. Playback / HUD chrome (`Skip freeze`, Knife label, toolbar titles) — not formula names.
11. Sidebar tabs, dialogs, playbook chrome (buttons, empty states). Keep user-typed titles as stored.
12. Analyzer-only strings (habits filters, series bar). DEV layouts editor last or skip.

### Phase 4 — FAQ / content strategy

13. Either leave articles EN-only or add `faq/pl/` dual files and locale-aware `FAQ_ITEMS`.
14. Still no KaTeX, no `react-markdown` on the client.

Tutorial copy, when that feature lands, is a **consumer of Phase 1–2**, not a phase of this plan. It should import `useMessages()` / `t()`, not ship its own dictionaries.

## Non-goals (v1)

- **Auto-detect only** — no override in Settings. Sniffing `navigator.language` as a *default for a brand-new* settings row is optional; a trapped PL or EN user must be able to switch.
- **More locales than `en` / `pl`.** Adding a third language is a catalog + `Locale` union change later, not a framework migration.
- **Translating parser / stats formulas.** ADR, trades, KAST, knife-round detection, OT scoring stay as in `analysis.rs` / `stats.ts`. Do not localize constant names, CSV column letters that tools parse, or Rust error text.
- **Translating map callouts, weapon names, or user notes.**
- **RTL, locale-specific fonts, or a translation TMS.**
- **KaTeX / math / client remark.** FAQ stays compiled HTML.
- **URL-driven locale** (`/pl/faq`) in v1 — one origin, one SPA, locale in IndexedDB. Share links stay `?map=&playbook=&strat=`.
- **Server-side or crawler-specific locale.** There is no app server.

## Risks

- **Test drift** — many tests query `getByRole(..., { name: "Export CSV" })`. Default locale stays `en` in tests; do not change the Vitest locale. After a string moves into the catalog, assert the EN catalog value (or import `en.header.exportCsv`) so a copy edit updates one place.
- **Incomplete PL** — `satisfies Messages` is the gate. Do not ship `en` keys with empty PL strings.
- **Stale settings** — unknown `locale` from a future schema must fall back to `en`, same as other `parseUserSettings` fields.
- **Flash of English** — settings load async from IDB. Accept a first-paint EN frame, or persist last locale in a tiny sync read later; do not block first paint on IDB.
- **Mixed language** — Phase 2 chrome + English FAQ is OK if labeled as such; avoid half-translated HUD mid-phase (finish a surface).

## Testing

- `en` and `pl` both satisfy `Messages` (typecheck is the test; optionally iterate keys).
- `t` interpolates and does not throw on extra vars.
- `parseUserSettings({ locale: "pl" })` / invalid / missing.
- Settings picker updates catalog (component test, EN default).
- FAQ: existing markdown compile tests unchanged until Phase 4. Keep the “no KaTeX / no math” assertion.

## Relation to other todos

- **USER-SETTINGS** — `locale` moves from the v2 table into v1 schema. Theme stays deferred. Settings modal / gear is the switch. Reset-to-defaults includes `locale: "en"`.
- **Tutorial** — consumer only. That work (separate plan/PR) must not add `todos` coupling here; it reads the shared catalogs once both exist. Do not block i18n skeleton on tutorial, and do not put tutorial markdown into this plan.
- **Playbook / PDF** — chrome strings go through catalogs when those UIs are wired (Phase 3). Exported PDF/CSV language is an open question; default EN for machine-readable CSV.
- **FAQ compile** (`faq-markdown` plugin) — content phase only; do not regress to runtime markdown.

## Open questions (whiskeyo)

1. **First visit:** always `en`, or seed `pl` when `navigator.language` starts with `pl` (still overridable)?
2. **FAQ v1:** EN-only articles + translated chrome, or dual `en`/`pl` files from the start?
3. **English region:** `en-US` vs `en-GB` for dates (`11 Sept` vs `September 11`)? Product copy is already US-leaning.
4. **Money:** keep `$1,234` (`en-US`) in both locales, or format with `pl-PL` (space/nbsp, different `$` placement)?
5. **CSV / PDF:** always English headers (tools, Discord paste), or follow UI locale?
6. **Industry words in PL:** leave “drop”, “eco”, “playbook”, “clutch” as loanwords, or prefer Polish coaching slang? Catalog can mix; needs a house style.
7. **Settings UI timing:** add a one-line Language select on today’s gear menu, or wait for the USER-SETTINGS modal and only add the field in the store until then?
8. **`<html lang>` on first paint:** worth a blocking sync cache, or is a one-frame `en` acceptable?

## One-line scope

**I18n v1 = English default + Polish catalogs, a typed helper (no i18n framework), `locale` on the existing user-settings document, chrome/settings first; FAQ strategy and tutorial are consumers, not a new stack.**
